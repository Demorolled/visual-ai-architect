## 1. Motivation

The engine (`backend/src/blueprint/bible.ts`) matches a user's natural-language
goal to a **strict JSON `Blueprint`**:

```ts
interface Blueprint {
  app_type: string;
  description: string;
  keywords: string[];
  target_stack: { frontend: string; backend: string; database: string };
  architecture_checklist: string[];
  wiring_graph: { source_module: string; destination_module: string; data_passed: string }[];
}
```

A stock LLM (a) drifts into conversational prose, (b) invents `target_stack`
fields that don't exist, or (c) omits `architecture_checklist` modules. This
dataset fine-tunes the model to **always emit valid, uncorrupted blueprint JSON**
that passes `loadBlueprints()` validation — regardless of how the user phrases
the request.

## 2. What the model learns (behavior, not facts)

Each example is `user request → blueprint JSON`:

```json
{
  "instruction": "I want a home media streaming app to play my music and video anywhere in my home",
  "input": "",
  "output": "{\"app_type\":\"home_media_server\",\"description\":\"...\",\"keywords\":[...],\"target_stack\":{...},\"architecture_checklist\":[...],\"wiring_graph\":[...]}"
}
```

The weights hardwire:
- **Shape fidelity** — always a JSON object, never prose, no markdown fences.
- **Exact key names** — `target_stack` is an object, `wiring_graph` is an array
  of `{source_module, destination_module, data_passed}`, etc.
- **Completeness** — every contract key present; checklist modules come from
  the real blueprint, not hallucinated.

## 5. Quality controls (built into the builder)

1. Every output re-parses as JSON and contains all 6 contract keys.
2. `wiring_graph` and `architecture_checklist` are validated as arrays.
3. Instructions are deduplicated.
4. Split is deterministic (seed 42), 90/5/5.
5. Builder aborts (`SystemExit`) if any example violates the contract.

## 6. Intended use

- **Round-3 QLoRA**: `scripts/launch-qlora-blueprint-round3.py` mixes this
  dataset (seeded sample) with existing `train.jsonl` to avoid catastrophic
  forgetting of code-generation skills, then exports GGUF.
- **Pairing with RAG**: at inference, the bible (`bible-reference/`,
  `data/code-bible/`) is injected via vector/keyword retrieval so the model's
  JSON output is grounded in pre-approved modules. Fine-tuning guarantees the
  *shape*; RAG guarantees the *facts*.

## 8. Known limitations

- 34% of instructions are template-generated; phrasing diversity is decent but
  not as rich as the 66% real prompts.
- The 5% test split is small (61) — use it as a smoke check, not a benchmark.
- Blueprints are mostly React/Express/SQLite stack; minority stacks exist
  (Go, FastAPI, Postgres) but are under-represented.
