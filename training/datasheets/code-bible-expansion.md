## 1. Motivation

The atomic code-chunk library is the LLM's "snap-together" source: each chunk
is a single-purpose, interface-standardized code component that the VACA
planner/generator retrieves and wires into plans. The library previously
covered 10 categories (UI / API / LOGIC / STATE / DATA / CRYPTO / GAME /
MEDIA / SYS / NET) with 204 chunks. Domains like **machine learning, LLM tooling,
DevOps, databases, observability, security, browser internals, mobile,
testing, graphics, math, and realtime** had **zero** chunk coverage — the model
had to improvise those components from scratch.

The first expansion added **300 atomic chunks across 12 new categories** (ML,
LLM, DevOps, DB, observability, security, browser, mobile, testing, graphics,
math, realtime). This second expansion adds **400 more across 16 new
categories** — algorithms, architecture, strings, collections, filesystem,
time, messaging, HTTP, accessibility, i18n, finance, education, codegen,
visualization, CLI, and embedded — so the model has pre-approved, RAG-
retrievable building blocks for those domains too.

## 2. What each chunk contains

Every chunk is a strict 3-rule component (atomic · standardized interface ·
semantic metadata):

```python
{
    "id": "ml-cosine-sim",            # slug = bible-reference/<id>/ dir name
    "name": "Cosine Similarity",
    "category": "ml",                  # one of the 12 new category codes
    "lang": "typescript",              # 100% TypeScript (matches VACA stack)
    "when": "Measuring vector similarity for retrieval / dedupe",
    "why": "Atomic metric: two vectors in, cosine distance out",
    "tags": ["ml", "vector", "similarity", "cosine", "embedding"],
    "iface": "export function cosineSimilarity(a: number[], b: number[]): number",
    "code": "export function cosineSimilarity(a, b) { ... }",
    "provides": "cosineSimilarity(a, b)",
}
```

Each chunk renders as `bible-reference/<slug>/00-index.md` with the interface
contract in a `ts` fence and the implementation in a `ts`/`tsx` fence, so the
loader (`loadBibleFiles`) injects it into codegen context verbatim.

## 6. Provenance & dedupe guarantees

- **No overlap with prior 504** — batch-3 ids are prefixed `alg- arch- str-
  col- fsys- time- msg- http- acc- i18n- fin- edu- gen- viz- cli- embed-`,
  categories disjoint from both the original 10 and the batch-2 12;
  cross-checked at load (duplicate-id detection across all 38 files aborts the
  scaffold).
- **Content-level dedupe** — each chunk targets a distinct capability (verified
  by unique id + when/why pair); per-category topics are mutually exclusive
  (e.g. `alg-binary-search` vs `mth-vector3` vs `ml-cosine-sim`).
- **Deterministic regeneration** — all 400 entries are re-derivable from the
  Python DB via the wire + scaffold scripts; rerunning is idempotent.

## 7. Intended use

- **RAG injection** at inference: `getLibraryContext` /
  `getLibraryContextForNodeType` retrieve the new chunks by semantic/keyword
  match, so plans and generated code for ML/LLM/DevOps/DB/security/etc. apps
  use pre-approved components instead of hallucinated ones.
- **Blueprint tagging**: future `build-blueprint-finetune-dataset.py` runs can
  attach these chunk slugs as semantic tags (prior coverage was 96–98% of 204;
  now ~100% of 504 is available).
- **Knowledge foundation** for a future chunk→app-type fine-tune round.

## 8. Known limitations

- All chunks are TypeScript — Python/Go/Rust variants exist only as language
  mappings, not separate chunk files.
- Chunk `code` fields are compact implementations (avg ~12.5 lines), sized for
  RAG injection; they are *components to snap together*, not full applications.
- The 28 new categories are curated but not exhaustive — future rounds can add
  more (e.g. `iot`, `hls`, `geo`).
